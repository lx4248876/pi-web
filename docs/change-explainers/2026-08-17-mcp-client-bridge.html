改动理解：MCP 客户端桥接（把 MCP 服务器工具接进 pi-web）

Deep 生成于 2026-08-17；基于仓库只读核实（Grounding 来自 lib/rpc-manager.ts、lib/tool-composition.ts、@earendil-works/pi-coding-agent 0.81.1 类型声明）。

⛳ 风险提示：本项新增「对外工具注册」链路并新增一项运行时依赖（MCP SDK）。工具一旦注册给模型，模型可触发任意 MCP 服务器暴露的动作——这属于能力面外扩，需注意只加载用户配置里的服务器、且对服务器进程的生命周期做清理，避免向会话注入不受控工具。

一句话

让 pi 会话能加载用户在 ~/.pi/agent 下配置的 MCP 服务器，把每个服务器暴露的 tool 映射成 pi 的工具（走 defineTool 的 customTools 通道），使模型能像 Codex 的 mcp 工具一样调用外部 MCP 生态。

改动地图

lib/mcp-client.ts（新增） · connectMcpServers / buildMcpToolDefinitions — 新建一个纯 Node 侧 MCP 客户端封装，负责读取配置、启动 stdio/SSE 服务器、握手并列出工具。
怎么改 / 为什么

怎么改：引入官方 @modelcontextprotocol/sdk（走 stdio transport 优先，这是 Codex 和绝大多数 MCP server 的主方式）；新增配置读取文件，格式是一个 JSON 列表（server 名 + command/args/env）。连接后调用 listTools 拿到每个 server 的工具清单。

为什么：pi-web 及其底层 pi-coding-agent dist 里没有 MCP 客户端（核实确认为零），这是唯一从零补齐 Codex 该能力的通道。独立成 lib/mcp-client.ts 是为了不把生命周期管理和工具描述混进 rpc-manager.ts 的会话编排。

lib/mcp-tools.ts（新增） · toPiTool / jsonSchemaToTypeBox — 把 MCP 工具的 JSON Schema 转成 defineTool 需要的 TypeBox schema，并把 MCP 的 call 结果转成 pi 的 tool result。
怎么改 / 为什么

怎么改：MCP 工具参数是 JSON Schema；pi 的 defineTool.parameters 收的是 TypeBox（见 types.d.ts:335），需要一层映射（存在 @sinclair/typebox Value/Type 构造或手工按类型递归）。调用时把模型给的参数透传给 MCP server 的 callTool，返回的 content 块（text/image/resource）归一成 pi 文本结果，多块拼接。

为什么：两边的 schema 方言不一样，不翻译就无法注册；结果里可能混有图片等内容块，需要折叠成 pi 认得的文本/结构。

lib/rpc-manager.ts · startRpcSession（:1229 处 createAgentSession 调用） — 把 MCP 工具合并进 customTools 一起传给 createAgentSession。
怎么改 / 为什么

怎么改：在 startRpcSession 里、调用 createAgentSession 之前，异步加载用户已启用的 MCP 服务器，把产出的工具定义和现有 createCompatUiTools() 结果拼在一起再传给 customTools。

为什么：这里是全仓库「额外工具」的唯一注入点（当前只注入 question）。挂在这，MCP 工具就会和内置工具、扩展工具走完全相同的生命周期，也被 composeActiveTools 的「非内置工具自动保留」规则覆盖，用户不用在 preset 里手动勾选。

app/api/mcp/route.ts（新增） · GET / POST — 一个读/写 MCP 服务器配置的 HTTP 端点，落盘到 ~/.pi/agent/mcp.json。
怎么改 / 为什么

怎么改：GET 返回当前配置（脱敏 env）；POST 校验后用 writeFileSync 写 getAgentDir()/mcp.json（沿用 lib/ui-state.ts 的持久化先例）。配置改动不要求重启即可在下次新会话生效。

为什么：pi-web 是 Web UI，配置不能只靠手编文件；且 ~/.pi/agent 下已有 settings.json/ui-state.json 的同目录先例，放这里是本机级、跨浏览器源共享，符合仓库既有约定。

components/ModelsConfig.tsx 或新独立面板 components/McpConfig.tsx · 配置表单 — 让用户在 UI 里增删 MCP 服务器。
怎么改 / 为什么

怎么改：给「服务器名 + command + args + env」做一个增删表单，调用上面新路由。为控制改动面，倾向新建 McpConfig.tsx 挂在现有设置区，而不是再拆 ModelsConfig.tsx。

为什么：这是让功能「看得见、配得了」的最小 UI 面；不建则只能手编 JSON，不算完整补齐。

components/MessageView.tsx · toolCall/toolResult 渲染（:981、:1161 附近）— MCP 工具调用结果的可读展示。
怎么改 / 为什么

怎么改：不强制改；MCP 工具调用本身会以标准 toolCall/toolResult 事件流入，现有渲染已能显示名称和文本。若某 MCP 返回长 JSON/多块，可后续再增强。

为什么：先保证「能跑通」；展示增强属于体验项，放后续，避免这项第一版改动面失控。

逻辑链路

用户在设置里配 MCP 服务器→ app/api/mcp 落盘 mcp.json→ startRpcSession 读配置→ lib/mcp-client 连接+listTools→ lib/mcp-tools 转 defineTool→ customTools 注入 createAgentSession→ 模型调用 → MCP callTool → 结果回显

改完你应看到

  • 配置一个真实 MCP server（例如一个 playwright 或 filesystem 服务）后，getAllTools() 里出现该 server 暴露的工具，模型在非 Off 工具预设下能调用它们。
  • 调用一个 MCP 工具，回答里能看到它实际返回的结果（文本），不再只有内置 7 个工具。
  • 填一个非法 command 或连接失败，会话能降级（跳过该 server 并给一条可见提示），而不是整场会话崩掉。

先别动

  • 不要重构 rpc-manager.ts 的会话编排或 tool-composition.ts 的 preset 逻辑——MCP 工具天然走「扩展工具」通道，现有逻辑已覆盖，无需改。
  • 不要顺手做「拆大文件」那项重构——那是清单最后一项，单独确认后再做。
  • 不要在这版就接 SSE/远程/无头浏览器 MCP server 的全矩阵；第一版只保证 stdio 主通道，其余留作扩展。

未知与假设

  • 未知：MCP 部分工具参数 schema 用到了 JSON Schema 里 TypeBox 没有 1:1 对应的关键字（如 anyOf/oneOf/复杂 $defs），映射的完整覆盖度待实现时逐个验证。
  • 未知：listTools 返回的工具描述可能与 pi 的 description/promptSnippet 字段语义不完全一致，需要看实际 SDK 返回再对齐。
  • 假设：官方 @modelcontextprotocol/sdk 可在当前 Node 版本下正常安装使用，且与 Next.js 服务端（Route Handler）同进程运行无冲突。
  • 假设：MCP 服务器进程由 pi-web 侧 spawn 并随会话生命周期管理是可行的（后续会话热加载、换 cwd 等边界需在实现阶段确认）。
  • 材料：够——主链路（工具注入点、defineTool 签名、配置目录、前端展示）均已核实到文件与符号。
