改动理解：新建会话发送后，左侧会话列表立刻刷新

Standard 生成于 2026-08-14；基于仓库只读核实（commit 1689a44）。

本改动未命中高风险词（认证/支付/删数据等）。为纯前端新增一个「会话文件落盘时点」的回调刷新。

一句话

新建会话发第一条消息时，左侧列表要等 agent 跑完一轮才出现。它刷新的时机是「事件」不是“文件好了”那一刻，所以加一个在「新会话第一条助手回复落盘」时触发列表刷新的回调，让新会话立刻出现在左侧。

改动地图

hooks/useAgentSession.ts · UseAgentSessionOptions + handleAgentEvent（message_start/message_update 分支）
怎么改 / 为什么

新增一个可选回调 onSessionContent（或类似名）。在 handleAgentEvent 的 message_start/message_update 分支里，用 ref 按 sessionIdRef.current 去重，每个会话只在「第一条」助手消息时调一次这个回调。

为什么落这：pi 的新会话 .jsonl 文件是「第一条 assistant 消息出现时才写盘」，而 message_start 正是这条消息生成的时刻——此时文件已在磁盘上，此刻触发刷新列表才能扫到它。

components/ChatWindow.tsx · Props + 传给 useAgentSession 的解构
怎么改 / 为什么

在 Props 增加 onSessionContent?，并像 onAgentStart 一样作为 prop 传进 useAgentSession，把最外层回调一路透传下去。

作用：把 AppShell 的刷新回调桥接到 hook 内部。

components/AppShell.tsx · handleAgentStart 旁的刷新回调 + 传给 ChatWindow
怎么改 / 为什么

新增 handleSessionContent（内部就是 `setRefreshKey(k => k + 1)`，与 handleAgentStart 同款），并在渲染 ChatWindow 时传成 onSessionContent。

刷新 key 一变，侧栏 useEffect 就重新 fetch /api/sessions，这次能扫到已落盘的新会话。

components/SessionSidebar.tsx · loadSessions（只波及，不改）
为什么波及

它已经是「refreshKey 变化就重拉列表」的入口，本次不新增逻辑；正好被 AppShell 新的 key 递增驱动，行为一致，无需改动。

逻辑链路

新会话发消息→ pi 生成第一条助手消息并写盘→ hook 的 message_start 判新会话→ onSessionContent 回调→ AppShell refreshKey+1→ 侧栏重新 fetch /api/sessions（这次能扫到文件）→ 新会话立即出现在左侧列表

改完你应看到

  • 新建会话发第一条消息后，稍等模型开始回复（第一条内容出现）时，左侧会话列表就已出现该会话，不用等整轮跑完。
  • 已有会话的列表刷新行为、刷新按钮、terminal 圆点等不受影响。

先别动

  • 不动服务端 /api/sessions 与 pi 的落盘策略（SessionManager._persist）——那是 pi 库行为，保持惰性写盘即可。
  • 不给侧栏加轮询/定时器，保持当前「事件驱动」刷新设计。
  • 不改会话排序、项目折叠、归档等无关逻辑。
